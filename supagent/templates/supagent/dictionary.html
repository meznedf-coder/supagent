Catalog

What people know about the data, one entry each: the glossary, one entry per index, groups of metrics, relationships, health checks, the rules the agent always follows, guides (documentation, runbooks, how-tos) and formulas. Each entry keeps its history, so a mistaken change or deletion can be restored. Entries marked agent were written by the agent from evidence it can check.

Documents and sites

Documents the agent searches: text, Markdown or HTML files, web pages and sites, wiki spaces (Confluence) and repositories (Bitbucket), read again every few days. Each page is cut in pieces kept in the knowledge search (words and meanings: PostgreSQL text search and pgvector when Superset's database has them), so the agent finds the passage a question needs and names its page. A site behind a sign-in is read with its token or password, kept encrypted and sent only to that site. Intranet addresses are read only when their domain is in the setting docs.allowed_domains (Settings).

The token is kept encrypted and sent only to this site. What it reads becomes searchable by everyone who can open the Data dictionary: use a token that only reads what they may see.

Notes

What users write down in a few seconds (in the chat: Notes, or /note … in the question box): what a meeting decided, a fact the team must not lose. The agent finds them, says whose note it is and of which day, and never takes one as a rule. An admin may pin a note for everyone, or make a catalog guide of it (then verified).

Categories

Every piece of knowledge is classified, in this platform's own words: functional or technical, its subjects, the applications and the components it is about, and your own categories (server, environment, team…). The LLM classifies what changes every day and may propose new values; a new value is used once an admin approves it. An admin also adds a value here (used at once) and, with Edit, moves a value to another category or says what it is part of. The router and the search use them to find the knowledge a question needs; the System map draws them.
Categories and where their values come from
Read from the data's fields
Subject, application and component, and your own (server, environment, team…). A category can read its values from the data: the fields whose names match its pattern (e.g. ^(host|node|server)$); two such fields of one index tell which values go together, proposed to you as "part of" in To review. Edit changes the name of one of yours (its values follow) and the field names of any; Remove takes one of yours away with its values and everything that names them (it asks first).

    System map

    Export:
    The architecture of the system as the categories describe it: one column per category (subjects, applications, components, servers…), each part in its box with what it does (its description, else a sentence of the documents that name it), a grey line from a part to what it is part of, and the interactions between parts (depends on, sends data to, calls…) as arrows. A big category is folded into one box: click it to open it. It follows the categories by itself (read again every 20 seconds while you look at it, not after 15 minutes with nobody at the page: a new part or a new "part of" is outlined for a moment) and the data: a part whose items are gone says so. It draws the approved values: a proposed one comes once approved in To review. Admins: Edit to move the boxes, draw an interaction (click a box, then another), and write what a part or an interaction is.
